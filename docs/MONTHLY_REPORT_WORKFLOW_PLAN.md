# Monthly report workflow — plan for the five October 2026 gaps

Status: design only, nothing implemented. Written 2026-11-11 for the next
implementer (senior-architect). Mock-up: [mockups/monthly_reports_page.html](mockups/monthly_reports_page.html).

User: the O&M engineer who closes the Tashkent month (project 1, ACWA RIVERSIDE
BESS) on the office desktop, at the start of the next month, with the SCADA
exports, the customer's Daily Generation Report and the CPTW permit register.
October 2026 had to be generated by a script outside the app. Goal: the next
month is made entirely on the Monthly Reports page, with no extra typing
beyond the one sentence only a person can write.

### Existing defects found while reading (fix inside this work)

* **D1 — Fix buttons for `inputs.*` questions do nothing visible.**
  `_goto` calls `self.tabs.setCurrentWidget(self._inputs_tab)`, but that widget
  is no longer a tab (it lives on the Availability page). The row gets selected
  on a page the user is not looking at. Fix: after selecting the row, if
  `self.tabs.indexOf(self._inputs_tab) < 0`, `self.open_availability.emit()`.
  Found by reading the code, not reproduced.
* **D2 — April/June permits are listed as October permits.**
  `load_cptw_register` takes a datetime cell at face value. In the register,
  some Issue Date cells were stored by Excel with day and month swapped
  (CPTW-APRS-312: Issue `2026-10-04` as a datetime, Valid till `13/4/2026` as
  text). Run against the real file for October it returns 17 permits, three of
  which (312, 313, 427) are from April/June. Every month with a day ≤ 12 is
  exposed. Customer-visible (section 6 permit list).
* **D3 — `asset_tree_service.reapply_exclusions` drops PM-stop tags.**
  It re-tags stored alarms from exclusion windows only; alarms the generator
  tagged `Preventive maintenance` (PM-covered stops) are reset to "not
  excluded". Called from Equipment after an exclusion is added. Not in scope
  to change Equipment's call, but step 5 must not call it as is (see below).

* Register with "Issued To" empty, or `issued_to` set to a party with no

* The existing manual type **"Customer POI file"** stays exactly as it is (see

After a Save from any of these dialogs the check re-runs (`_run_check`).
The check itself stays read-only: every write happens in the PM dialog the
user confirms.

**Rules (service)** — new function `report_precheck_service.permit_questions(project_id, year, month, ws_long=None)`, called from `run_precheck` for `site == 'tashkent'`:

1. Permits: the month's `permit_register` file →
   `load_cptw_register(path, y, m, issued_to=cfg.permit_issued_to)` (same
   filter as section 6).
2. PM permit: title matches `(?i)preventive|\bPM\b|KKS`; status does not
   contain `cancel`.
3. Blocks from the area text: `(?i)RMU[\s\-]*0*(\d{1,3})` plus following
   `[/,&]\s*0*(\d{1,3})` lists (`BESS Zone3 RMU-22`, `RMU-06`, `RMU-21/22`).
   **RMU number = plant block 1..N** (`num_blocks`), compared directly with
   `pm_activities.affected_blocks` (plant numbering). Never translate through
   containers/zones. Numbers outside 1..N → ignored, counted in the ℹ row.
4. Permit dates = issue … valid-till inclusive (missing valid-till = issue
   day). A PM record matches when same block and its date lies in that range.
5. PM records: `rw.get_pm_activities(project_id, y, m)` split to block-days the
   way `pm_as_unavailability` does; whole-plant (`all`) records are skipped for
   the PTW and permit checks.
6. Stops: `T.pm_stop_windows(ws_long, records)` — the same definition that
   lets a PM cover its stop (longest out-of-operation run overlapping
   07:00–19:00). For "permit without record", call it with a synthetic record
   `{pm_id: None, block, date_from: d, date_to: d, hours: 0}`.
7. Load the working status once per `run_precheck`: refactor `edge_questions`
   to take an optional `ws_long`, and load it in `run_precheck` when the file is
   present (it goes through `parse_cache`).
8. "Probably a duplicate" = same block has another PM record in the month
   that does have a permit or a stop.

Question dicts gain an optional `prefill` (dict for the dialog). New targets:
`inputs.pm.add` (prefill) and `inputs.pm.ptw` (ref = PM id, prefill
`{'ptw_no': ...}`); `_goto` opens `PMDialog` directly from the Monthly page
(the dialog class lives there) instead of navigating.

**Edge cases**: register lists the same block twice the same day (two
permits) → one question; PM record dated a day after a multi-day permit →
inside range, fine; permit on the last day of the previous month and PM record
on the 1st → not matched (Q8); locked month → dialogs refuse with the existing
`MonthLockedError` message; no SCADA file → only PTW and permit-without-record
checks (permit rows then have no stop text and are ⚠); very large register
(2,000 rows, mostly empty) — openpyxl full read takes ~1–2 s, acceptable,
cached result not needed.

**Must not change**: no PM record, exclusion or permit is written by the
check; existing question kinds and their order; `needs_confirmation`.

### Item 4 — Exclusion types "KKS work" and "Dispatch instruction"

**How the type is used today** (all call sites checked):

| Use | Effect of a new type |
|---|---|
| `calculate_plant_excluded_hours` / `calculate_excluded_hours`: total excluded hours | **None** — summed over all types; a window gives the same number under any type. |
| `breakdown` dict (seeded from `EXCLUSION_TYPES`) → "Exclusion Type" table in the report (rows with h > 0) | New row label only. |
| Tashkent "Scheduled unavailability (PM)" row = `breakdown['Scheduled Maintenance']` | Unaffected for existing rows. A window typed "KKS work" does **not** enter that row (KKS is not PM). |
| `planner_service` last-PM date reads `exclusion_type='Scheduled Maintenance'` | Unaffected; KKS windows correctly not counted as PM. |
| Alarm tagging (`match_alarm_to_exclusions`, `excluded_by` text) | Tag text only — see Dispatch rule below. |
| `validate_window` / `add_exclusion` / `update_exclusion` check membership | Accept the new names once appended. |
| Combos: `ExclusionDialog`, `equipment_page`, `work_log_form` iterate the list | New entries appear; defaults unchanged when **appended**. |
| PWA `backend/static/index.html` has its own list | Not changed this round (phone events are confirmed on the desktop, where the type can be set). |

**Change**

* `EXCLUSION_TYPES` append `"KKS work"`, `"Dispatch instruction"` (append, so
  index 0 stays "Scheduled Maintenance"). Update the module docstring and the
  `db_manager` comment.
* `ALARM_NEUTRAL_TYPES = {"Dispatch instruction"}` in `availability_service`;
  `match_alarm_to_exclusions` skips those windows. Reason: a half-month
  whole-plant dispatch window would otherwise hide every genuine fault of that
  fortnight from 3.2 / 5.1 / 5.2. Availability handling is unchanged (Q1).
* `ExclusionDialog`: one hint line under the Type combo that follows the
  selection (`currentTextChanged`):
  * Scheduled Maintenance — *Planned stop by the O&M team. Counts in "Scheduled unavailability (PM)".*
  * Grid Outage — *Utility-side loss of the grid.*
  * Force Majeure — *Events outside anyone's control.*
  * Major Fault — *Exceptional fault to be reviewed separately.*
  * KKS work — *Planned KKS / EPC work under a permit. Excluded like any window; not counted as PM.*
  * Dispatch instruction — *Blocks held out of operation on the dispatcher's order. Excluded from availability; alarms inside the window still count as faults.*
* No data migration: existing "Scheduled Maintenance" KKS windows stay as they are.

**Edge cases**: exclusions with NULL project/year/month are selected by
`get_exclusions` exactly as before (type plays no part in the query); a type
string not in the list (older DB, typo) still sums in calculations
(`breakdown.get(t, 0)`), as today.

**Must not change**: any availability percentage; August golden;
defaults of the combos.
